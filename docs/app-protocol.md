# Прикладной слой: протокол, имена, клиент/сервер, роли

*Версия 0.1 — 2026-06-23. «Как overnet выглядит для человека»: что в адресной
строке, как устроены клиент и сервер, какие бывают узлы.*

---

## 1. Самодостаточность + опциональный выход в clearnet

**По умолчанию overnet самодостаточен.** Адресат — всегда узел overnet; имена
`.ov` резолвятся **внутри** сети; сервис достижим через onion-маршрут **без
публичного IP и без DNS** (как Tor onion-сервис). Clearnet не нужен вообще — это
и есть «неубиваемость»: нечего блокировать на границе.

**Опциональный выход в clearnet** — отдельные **exit-узлы**, которые включаются
**явно и по желанию**. Важно честно: выход возвращает все проблемы exit-нод
(злоупотребления, блокировки, юридические претензии к выходу). Поэтому:
- выход **выключен по умолчанию**, узел становится exit только осознанно;
- выход визуально помечен (пользователь видит, что покидает overnet);
- самодостаточная часть от наличия/отсутствия выхода **не зависит**.

## 2. Протокол: не переписываем HTTP — разделяем схему и провод

HTTP плох не семантикой, а **транспортом**: открытые заголовки, SNI, утечка
метаданных, привязка к TLS/TCP. В overnet транспорт уже решён (onion + Noise +
`Link`), поэтому:

- **Схема — своя:** `overnet://search.ov`. Это всего лишь маркер «говорить по
  overnet» + имя для резолва внутри сети. Дёшево и видно в адресной строке.
- **Провод — семантика HTTP внутри overnet-сессии.** Запрос/ответ, методы, типы
  контента, коды статусов — это универсально и переиспользует весь веб (HTML/CSS/
  JS, рендеринг, инструменты). Несём это **внутри зашифрованной onion-сессии**, как
  HTTP/3 поверх QUIC или как Tor onion-сервисы поверх обычного HTTP.

**Почему так исчезают пороки HTTP:** заголовки/SNI/метаданные — это транспортный
слой; внутри overnet **нет открытого слоя для наблюдателя**, шифровано всё, включая
служебку. Ровно то «зашифровать пакет целиком», к чему ты шёл в начале — но
достигнутое архитектурой, а не переписыванием HTTP.

**Старт простой:** HTTP/1.1-подобный запрос/ответ внутри сессии. Мультиплексирование
в стиле HTTP/2 — позже. «Своё» останется ощутимым: `overnet://`, имена `.ov`,
всё-шифровано-по-умолчанию, серверам не нужен публичный IP/DNS — это уже другой веб.

> **Не изобретаем семантику HTTP с нуля** — это тарпит на десятилетия граничных
> случаев (кэш, диапазоны, content negotiation, стримы). Делаем своё там, где это
> даёт неблокируемость (схема, адресация, шифрование), не там, где это просто гордость.

## 3. Имена и bootstrap

- **`name.ov`** — человекочитаемое имя (petname-слой), резолвится в **криптоадрес**
  сервиса (= f(публичный ключ), см. naming.md). Доменов/центрального DNS нет.
- **`search.ov`** — well-known стартовый сервис (поиск + каталог имён). Его
  криптоадрес (публичный ключ) **вшит в клиент**, чтобы было с чего начать — как
  bootstrap/directory-узлы у Tor/Yggdrasil. Это «известный», а **не**
  «привилегированный» узел: вшитых сервисов может быть несколько, и их можно менять.
- Резолв `name.ov → криптоадрес` дают **directory-узлы** (см. роли) подписанными
  записями; ответы кэшируются и проверяются по подписи.

## 4. Клиент

Клиент overnet — это **узел сети** (ретранслирует по умолчанию: «участник = нода»)
**плюс локальный шлюз**, через который человек смотрит overnet.

Реалистично по шагам:
- **Сейчас:** локальный шлюз/прокси. Клиент держит локальную точку, через которую
  идут `overnet://`-запросы; простой UI рендерит ответы. Регистрация
  OS-обработчика схемы `overnet://`, чтобы ссылки открывали клиент. (Так делают
  I2P-прокси / Tor.)
- **Сильно позже (если вообще):** форк браузера ради полноценной адресной строки
  `overnet://` (как Tor Browser — форк Firefox). Свой браузер с нуля — это годы; не
  тратим на это силы на старте.

Bootstrap при первом запуске: сгенерировать личность (ed25519 → криптоадрес),
найти первого соседа (инвайт/QR от друга, вшитые bootstrap-узлы, локальное
обнаружение), решить PoW (позже). См. naming.md §«первый контакт».

## 5. Сервер / сервис

Сервер overnet = узел, который **отвечает по своему криптоадресу** (onion-сервис).
Свойства:
- **Не нужен публичный IP и DNS** — достижим через onion + rendezvous даже за NAT.
- **Адрес = ключ** — `search.ov` это petname поверх криптоадреса сервера.
- Отдаёт контент по семантике HTTP (см. §2): `GET overnet://search.ov/` → страница.

Это снимает огромный барьер: «поднять сайт» = запустить узел с ключом, без
хостинга, домена, белого IP и сертификатов.

## 6. Роли узлов — это капабилити, а НЕ иерархия статусов

Честная поправка: **привилегированная «иерархия статусов» опасна** — она
воссоздаёт централизацию и список мишеней (как публичный список релеев Tor). В
overnet узел **опционально берёт на себя роли** (капабилити), а доверие — это
ортогональные **уровни open/vouched** (см. trust-and-membership / architecture §2).

Роли (узел может совмещать несколько):

| Роль | Что делает | По умолчанию |
|------|------------|--------------|
| **Relay** | ретранслирует onion-трафик соседей | **вкл.** (участник = нода) |
| **Service** | хостит `.ov`-сервис (отвечает по криптоадресу) | по желанию |
| **Directory** | отдаёт подписанные записи `name.ov → криптоадрес`, помогает поиску | по желанию |
| **Rendezvous** | сводит два узла за NAT (точка встречи onion-сервиса) | по желанию |
| **Guard** | чей-то личный вход (скрытый, не публичный список) | по выбору клиента |
| **Exit** | выпуск в clearnet | **выкл.**, только осознанно |

«Иерархии» в смысле ранга нет. Есть:
- **капабилити** — что узел умеет/согласился делать;
- **уровни доверия** — open (любой) vs vouched (по рефералу), ортогонально ролям;
- **well-known сервисы** (`search.ov`) — «известные/вшитые», не «вышестоящие».

## 7. «Сеть поверх сети» — как это выглядит при тесте

- Поднимаешь несколько узлов (твои 3 загран + 1 домашний РФ). Каждый — relay.
- Один из них — **service** (`search.ov`-подобный) с известным ключом.
- Клиент с домашней машины: `overnet://<сервис>/` → запрос идёт onion-маршрутом
  через relay'и, сервис отвечает контентом. Релеи видят только соседей, не контент.
- Сначала транспорт-`Link` = TCP/ostp поверх интернета (фаза 1); тот же app-слой
  потом поедет по физическим `Link` без изменений.

## 8. Открытые вопросы

- Точный формат запроса/ответа: брать HTTP/1.1 как есть или слегка ужать заголовки.
- Резолв `name.ov`: модель доверия directory-записей (мульти-подпись? сверка
  отпечатка вживую, как safety number?).
- Где живёт UI: отдельное приложение-шлюз vs форк браузера и когда.
- Маркировка clearnet-выхода в UI, чтобы человек понимал, что покидает overnet.
